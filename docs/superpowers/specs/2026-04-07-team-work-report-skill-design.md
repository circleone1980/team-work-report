## 一、概述

### 1.1 背景
团队需要从禅道导出的Excel工作记录表单中，自动生成以业务为导向的周报/月报。现有流程存在以下问题：
- 项目分类过粗（如"泰擎II期"包含多个子业务）
- 人工整理耗时费力
- 临时性工作容易被遗漏
- 业务价值提炼不够清晰

### 1.2 目标
创建一个Claude Code skill，能够：
1. 自动解析禅道Excel工作记录
2. 智能识别和聚类业务类型
3. 生成团队视角的业务导向报告
4. 支持增量学习和规则演进

### 1.3 目标用户
- 团队负责人：需要生成团队周报/月报
- 项目经理：需要了解各业务进展
- 技术总监：需要掌握团队工作全貌

## 二、需求分析

### 2.1 功能需求

#### 必须有（MVP）
- ✅ 解析禅道Excel工作记录表
- ✅ 自动识别业务类型（LLM聚类）
- ✅ 生成Markdown格式报告
- ✅ 支持周报/月报模式
- ✅ 交互式确认业务分类

#### 应该有
- ✅ 规则文件持久化（增量学习）
- ✅ 分层报告结构（简洁总结 + 详细附录）
- ✅ 新业务自动发现机制
- ✅ 工时统计和占比分析

#### 可以有（未来）
- ⏳ 支持多语言输出
- ⏳ 集成图表可视化
- ⏳ 导出为Word/PDF格式
- ⏳ 与禅道API直接集成

### 2.2 非功能需求

- **性能**：处理200+条记录应在10秒内完成
- **准确性**：业务识别准确率 > 85%
- **易用性**：零配置启动，首次使用5分钟内上手
- **可维护性**：规则文件清晰易懂，支持手动编辑

**输入**：`2026年3月工作耗时统计表.xlsx`
- 12位员工
- 10个粗分类项目
- 170+条工作记录

**期望输出**：

### 3.3 核心模块

#### 3.3.1 ExcelParser
**职责**：解析禅道导出的Excel文件

**输入**：Excel文件路径

**输出**：
```python
{
    "month": "2026-03",
    "tasks": [
        {
            "person": "张三",
            "date": "2026-03-23",
            "project": "泰擎AI平台（T-Mind）II期",
            "detail": "完成学生画像8维度设计...",
            "hours": 4.0
        },
        ...
    ]
}
```

**技术选型**：openpyxl + pandas

#### 3.2.2 LLMCluster
**职责**：智能聚类工作记录，提取业务类型

**算法**：
1. 使用LLM分析任务语义
2. 识别业务边界（如"形成性评价" vs "报告批阅"）
3. 提取业务名称和关键词
4. 统计工时和参与人员

**提示词模板**：
```
分析以下{count}条工作记录，按业务类型聚类：

{tasks}

要求：
1. 识别5-10个主要业务
2. 提取简洁业务名称（如"形成性评价系统"）
3. 列出每个业务的关键词（3-5个）
4. 统计每个业务的工时和参与人数
5. 提供每个业务的示例任务（2-3条）

输出JSON格式（见schema）
```

**输出Schema**：
```json
{
  "businesses": [
    {
      "name": "形成性评价系统",
      "keywords": ["形成性", "学生画像", "8维度"],
      "total_hours": 120.5,
      "people": ["张三", "李四"],
      "sample_tasks": ["完成学生画像8维度设计"],
      "summary": "AI驱动全流程数字化..."
    }
  ]
}
```

#### 3.2.3 RulesManager
**职责**：管理业务分类规则文件

**规则文件格式**（`business_rules.md`）：
```markdown
# 业务分类规则

## 元数据
- 版本：v1.0
- 更新时间：2026-04-07
- 适用月份：2026-03

## 业务定义

### 1. 形成性评价系统
- **关键词**：形成性, 学生画像, 8维度
- **匹配规则**：`"形成性" in task OR ("学生画像" in task AND "8维度" in task)`
- **历史工时**：120.5h（2026-03）

### 2. 实验报告批阅
- **关键词**：报告批阅, doc, pdf, ocr
- **匹配规则**：`"报告批阅" in task OR "ocr识别" in task`
- **历史工时**：85.0h（2026-03）
```

**功能**：
- `load_rules()`：加载规则文件（如果存在）
- `save_rules(businesses)`：保存新规则
- `update_rules(new_businesses)`：增量更新规则

#### 3.2.4 Interactive
**职责**：交互式确认和调整

**交互流程**：
```
📊 识别到 5 个业务类型：

1. 【形成性评价系统】120.5h
   关键词：形成性, 学生画像, 8维度
   示例：完成学生画像8维度设计

2. 【实验报告批阅】85.0h
   ...

操作选项：
  [1-5] 修改业务名称
  [m1-2] 合并业务（如 m1-2 将1合并到2）
  [d1] 删除业务
  [a] 添加新业务
  [y] 确认并生成报告
  [q] 放弃

请选择：
```

**边界情况处理**：
- 未识别任务 > 30%：强制进入交互模式
- 用户选择合并：保留目标业务名称，合并工时
- 用户选择删除：将任务归入"其他工作"

## 四、关键技术决策

### 4.1 为什么选择LLM聚类？

**对比其他方案**：

| 方案 | 准确性 | 灵活性 | 零配置 | 可解释性 |
|------|--------|--------|--------|----------|
| LLM聚类 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| TF-IDF聚类 | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 规则匹配 | ⭐⭐⭐⭐ | ⭐⭐ | ⭐ | ⭐⭐⭐⭐⭐ |

**结论**：LLM聚类最适合零配置启动场景，后续通过规则持久化保证稳定性。

### 4.2 为什么需要交互式确认？

- **避免误分类**：LLM可能将"报告批阅"和"试卷批阅"混淆
- **发现新业务**：团队负责人最了解业务全貌
- **用户掌控**：报告代表团队形象，需人工把关

### 4.3 为什么使用Markdown作为规则文件？

- **可读性**：团队负责人可以直接阅读和编辑
- **版本控制**：Git友好的纯文本格式
- **可移植性**：不依赖特定工具

## 五、边界情况处理

### 5.1 数据质量

| 问题 | 解决方案 |
|------|----------|
| Excel格式异常 | 提示用户检查文件，支持多Sheet |
| 任务描述为空 | 跳过或归入"其他" |
| 工时数据缺失 | 使用0或提示用户 |
| 日期格式混乱 | 多格式识别 + 用户确认 |

### 5.2 聚类质量

| 问题 | 解决方案 |
|------|----------|
| 业务数量过多 | 提示合并相似业务 |
| 业务边界模糊 | 交互式拆分或合并 |
| 临时性工作 | 明确标注在报告中 |

### 5.3 规则演进

| 场景 | 处理方式 |
|------|----------|
| 业务下线 | 标记为 `deprecated`，不再匹配新任务 |
| 业务重命名 | 更新规则，保留历史关联 |
| 业务拆分 | 创建新规则，迁移历史数据 |
